## 修复 4399 token decode/parse failed

用户真机日志：`login data received (4399)` + `libcef hook installed` 都成功，但 `4399: token decode/parse failed`。

**根因（两处）**：
1. **截断**：`LoginSharedData.h` 的 `param0` 原为 `WCHAR[256]`，而密码登录入库的 token 是 `NetWork::DumpToken()` 产出的 TinyBase64('$')+JSON，4399 cookie（USESSIONID/Pauth/ck_accname 等长值）JSON 轻松 >255 字符，`wcsncpy_s(...,_TRUNCATE)` 截断成残缺 base64 → decode 抛异常。
2. **格式分歧**：DB 中 `m_token` 有两种来源——密码登录走 `net.GetCookie()`（=DumpToken，base64 JSON）；`HandleMenuEditDll` 走 `LoadCookieFromIni` 把老 ini 的**原始 cookie 串**（`NAME=VALUE; ...`）写进 m_token。旧 hook 只认 base64，原始串必失败。

**修复**：
- `LoginSharedData.h`：`param0/param1` 扩到 `WCHAR[1024]`（映射 64KB，余量足；字段偏移不变，仅总长变）。
- `TestLoaderHook.cpp`：`Apply4399Cookies` 改为双格式兼容——先试 TinyBase64→JSON，抛异常（原始串含 ';'，base64 表无 ';' 必失败）则走 `ParseRawCookie`（按 ';' 分段、取首个 '='、trim）解析原始 cookie 串。成功日志带 `(N of M, json|raw)`。
- 离线测试新增 `4399raw` 用例（`test_hook_login.cpp` + `run_tests.sh`）。

**验证**：P1 24 + P2 16 + 4399(base64)11 + 4399raw 11 + 台服 13 全过。DLL 已部署 Release/TestLoaderHook.dll。

**重要**：契约头改了，用户必须在 VS 重新「生成解决方案」重编 `Test_Loader.exe`（皮肤 zip 编译期嵌入，手工 build_all.sh 只产出 Test_Loader_test.exe）。否则旧 exe（256 大小）写共享内存只填前 1040 字节，新 DLL（4112 字节）读 param1（台服密码，偏移 2064）会是零——台服登录会失败。

## 修复 4399 token 解码尾组丢字节（Pauth/Pnick/Puser 对、末尾 '@' 乱码）

用户真机日志：`4399: token decode/parse failed` + json 解析报错 `parse error ... missing closing quote; last read: '"@'`，解码出的 JSON 前半段（Pauth/Pnick/Puser）完全正确，仅末尾变 `@` 乱码。

**根因**：不是截断（DB 的 token 列是 SQLite TEXT 不截断；param0[1024] 也装得下 252 字符 token），而是 **TinyBase64 解码函数自身的尾组 bug**。该解码逻辑从加载器 `TinyBase64.hpp` 抄来，与参考 DLL `version_x64_passNp::version.cpp:449` 逐字相同，都存在 `if (i <= len)` 判定错误：当原始 JSON 长度 %3==2 时，base64 剥掉 1 个 '$' 填充后尾组剩 3 字符（本应解出 2 个有效字节），但 `i<=len` 判定把第 2 个有效字节漏掉，导致末字节缺失 → JSON 被截断。参考 DLL 能跑通只是因为它的真实 cookie JSON 长度恰好避开 L%3==2 分支。

**修复**（`TestLoaderHook.cpp` 的 `TinyBase64::decodeToString`）：尾组字节数按「实际读到的字符数」精确决定——3 字符组解 2 字节、2 字符组解 1 字节、4 字符组解 3 字节。改用 `if (i+2 < len)`（byte1）/ `if (i+3 < len)`（byte2）判定，去掉错误的 `i<=len` 兜底。此修复对「带 $ 完整 token」与「$ 被丢只剩 3 字符尾组」两种情况都正确。

**注意**：该 bug 仅在 DLL 解码函数里，加载器只编码不解码，**只需重编 DLL 无需重编 exe**（但 param0[1024] 的 exe 重编仍建议做，以容纳超长 token）。

**回归测试**：`test_hook_login.cpp` 新增 `4399b` 模式，构造 JSON 长度 %3==2 的 token（76 字节 JSON + extra 字段），断言 `extra=z` 正确落库；旧解码会丢末字节导致 JSON 解析失败、cookie 全空。`run_tests.sh` 接入。**验证**：P1 24 + P2 16 + 4399 11 + 4399raw 11 + 4399b 12 + 台服 13 全过。DLL 已部署 Release/TestLoaderHook.dll。

## 编译坑：Edit 工具剥离 BOM/LF 致 C2512（dbwork.h）

用户 VS 编译报 `DbWork.cpp(177,14): error C2512: "UserInfo": 没有合适的默认构造函数可用`，但 dbwork.h 第 21 行明明有 `UserInfo() : m_nType(0), m_nIndex(0), m_serverId(0) {}`。

**根因**：本次 Edit 工具改写 `dbwork.h` 时，该文件被**去掉了 UTF-8 BOM 并被转成 LF 行尾**（其余 6 个被改文件 BOM+CRLF 完好）。MSVC 无 BOM 时按本地代码页 GBK 解析；第 20 行中文注释 `// 4399 服 ID（每账号独立，随账号存库）；0=最近服，台服无效` 里某全角字符尾字节恰为 `0x5C`（反斜杠），被当作 `//` 行尾的**行续接符 `\`**，把第 21 行构造函数吞进注释块 → 编译器看不到默认构造函数 → C2512。

**修复**：纯字节级（`[System.IO.File]::ReadAllBytes/WriteAllBytes`，不文本解码避免二次损坏）为 dbwork.h 补 `EF BB BF` BOM + 把孤立 `0A` 归一为 `0D 0A`。修复后 BOM=True/CRLF=True，构造函数可见，错误消除。

**铁律补丁**：本工程用 Edit 工具改 `.h/.cpp` 后，**必须校验 BOM+CRLF**（尤其含中文注释的头文件，如 dbwork.h）。缺失则行续接符吞代码，报各种诡异 C2512/C3861/CXXXX。批量校验脚本：`[System.IO.File]::ReadAllBytes` 看首 3 字节是否 `EF BB BF` + 扫描 `0D 0A`。

## 修复 capture 模式 set_cookie hook 挂载失败（时机错误）

真机日志：`[TestLoaderHook] login data received (capture)` 后报 `capture mode: get global manager / set_cookie failed`，抓取没生效。

## 修复 capture 稳定性（500ms 轮询 → 命令-应答握手）

用户指出 `visit` 是异步的，500ms 盲目轮询 visit+写回既浪费 CPU 又存在"读到早于回调完成"的竞争，提出**命令-应答握手**方案：exe 点"确定"后置标志位 → DLL 见标志才 visit → 写回 param0 并置就绪标志 → exe 轮询就绪标志（带超时）再读。

**实现**：
- `LoginSharedData.h`：`flags` 字段注释新增位 8/9 用途；新增宏 `TL_CAP_REQ=0x100`（加载器→DLL 请求抓取）、`TL_CAP_RDY=0x200`（DLL→加载器 param0 就绪）。**借用 flags 高位，不新增字段**（低 8 位仍给 sid，位 10..31 仍预留）。
- `TestLoaderHook.cpp`：
  - 删除 `CaptureThread`（500ms 空转 visit+写回）；改为 `DoCaptureOnce(p)`（清快照→ResetEvent→visit→`WaitForSingleObject(g_capDoneEvent,2000)` 等 visitor 完成→编码写 param0→`p->flags |= TL_CAP_RDY`）+ `CaptureIpcThread`（100ms 仅轮询 `flags & TL_CAP_REQ`，见到才调一次 `DoCaptureOnce`，平时空闲）。
  - 新增 `g_capDoneEvent`（手动复位）；`MyCookieVisit` 在末条（`count+1>=total` 且 `total>0`）或收到 `cookie==NULL` 终态时 `SetEvent`（2s 超时兜底，防 total==0 不回调导致死等/截断）。
  - `SetupCaptureHook` 起 `CaptureIpcThread`，日志 `capture: IPC thread started (wait for REQ)`。
- `CMainDlg.cpp`：`HandleMenuAddByDll`/`HandleMenuEditDll` 点"确定"后改为 `MapViewOfFile(hMap, FILE_MAP_ALL_ACCESS)` → `p->flags |= TL_CAP_REQ` → 轮询 `p->flags & TL_CAP_RDY`（10s 超时，100ms 步进）→ 命中才读 `p->param0`，否则 cookie 空走原"未捕获到"提示。

**握手时序**：exe 置 REQ(0x100) → DLL 清 REQ+visit+等完成(≤2s)+写 param0+置 RDY(0x200) → exe 轮询到 RDY 读 param0。无忙等、无竞争；抓完即止，进程存活期间线程仅轻量轮询 4 字节标志。

**需重编**：exe+DLL 一起（flags/param0 契约）。沙箱禁 msbuild，用户 VS 重新生成。预期真机日志：`capture: IPC thread started (wait for REQ)` → 点确定后 `capture: REQ seen, capturing...` → 登录后 `capture cookie: <name>` 多条 → `capture: done, RDY set`；加载器入库。若只到 `REQ seen` 无 `capture cookie:`：CookieStore 里无 4399 域 cookie（未登录成功或登录态不走 CEF cookie 存储，则须换读 CEF Cookies SQLite 文件方案）。

## 编译坑：本项目 CEF 是 3.2357（老版），cookie/request_context API 命名与新版不同

用户 VS 编译 capture 改动报 `C2039: "get_cookie_manager"/"visit" 不是成员`。**根因**：本工程用的 CEF 是 `cef_binary_3.2357.1291`（2015 版），头文件在 `C:\Users\MZPEDH\Downloads\cef_binary_3.2357.1291-master\...`。其 C API 命名与后来版本不同：

- `_cef_request_context_t` **没有** `get_cookie_manager`，而是 **`get_default_cookie_manager(self, cef_completion_callback_t* callback)`**（返回该 context 的默认 cookie manager）。
- `_cef_cookie_manager_t` **没有** `visit`，而是 **`visit_all_cookies(self, cef_cookie_visitor_t*)`**（还有 `visit_url_cookies(self, url, includeHttpOnly, visitor)`）。
- 全局 manager 取 `g_pGetGlobalManager(nullptr)`（即 `cef_cookie_manager_get_global_manager(callback)`），callback 传 NULL 即可。

**修复**：`GetEffectiveManager()` 用 `g_capReqCtx->get_default_cookie_manager(g_capReqCtx, nullptr)`；`DoCaptureOnce` 用 `g_capManager->visit_all_cookies(g_capManager, &g_capVisitor)`。

**铁律**：涉及 CEF C API 时，**必须对照本机 `C:\Users\MZPEDH\Downloads\cef_binary_3.2357.1291-master\...` 实际头文件**确认成员名，不能直接套用新版/网上的 `get_cookie_manager`/`visit`。以后凡是加 CEF 调用，先 `Read` 对应 `include/capi/cef_*.h` 核对签名。

## capture 崩溃修复（确定后 exe 崩溃）

用户点"确定"后加载器崩溃。**根因**：`CMainDlg.cpp::GetUserNameByCookie` 直接 `custom.decode()` + `nlohmann::json::parse()` 而**没有 try-catch**；DLL 侧 `Apply4399Cookies` 里同样的代码是有 try-catch 的。cookie 串一旦异常（截断/编码损坏/非 ASCII 经 CP_ACP 往返损坏）就抛未捕获异常 → 崩 loader。此外两个隐患：`MapViewOfFile(hMap, FILE_MAP_ALL_ACCESS, ...)` 在 PAGE_READWRITE 段上请求执行权限会返回 NULL（握手静默失效）；DLL 在 worker 线程调 `get_default_cookie_manager(g_capReqCtx, nullptr)` 是未验证路径，可能带崩游戏端。

**修复**：
1. `GetUserNameByCookie` 包 try-catch（catch std::exception，失败 OutputDebugStringA 后返回 L""，交由调用方按"未解析到用户名"处理，cookie 仍入库不丢）。
2. 两处 `MapViewOfFile` 的 `FILE_MAP_ALL_ACCESS` 改为 `FILE_MAP_READ | FILE_MAP_WRITE`。
3. DLL：`my_create_browser`（CEF 线程、已验证时机）直接 `g_capManager = g_pGetGlobalManager(nullptr)` 缓存全局 manager；`GetEffectiveManager()` 直接返回它（`g_capReqCtx->get_default_cookie_manager` 路径删除）。理由：Apply4399Cookies 已验证 4399 登录态就存于全局 manager，手动登录 cookie 同 store，且避免 worker 线程走带 callback 的未验证 C API。

**需重编**：exe + DLL 一起。`g_capReqCtx` 现仅赋值不再读取（静态全局，无报错）。预期真机日志：DLL 侧 `capture: IPC thread started` → 点确定后 `capture: REQ seen, capturing...` → `capture cookie: <name>` 多条 → `capture: done, RDY set`；加载器入库（不再崩溃）。
